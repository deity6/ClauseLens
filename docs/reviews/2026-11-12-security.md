> 对象：ClauseLens 条款透镜（前端 `https://lens.dohub.tech`，后端 `https://api.dohub.tech`）

> 审计期间（02:41:03、02:50:35）服务被**外部**重启过两次（`Deactivated successfully` → `Started`，`NRestarts=0`，非崩溃）；重启前后代码 md5 未变，报告里的进程号（520997/525948/528359）差异即由此而来。

## 总评：**打回**

三条各自独立、都已实测复现的问题，任何一条都不该带病对外：

| # | 一句话 | 后果 |
|---|---|---|
| **S1** | 抓回来的 HTML 进 `extract_text()` 时有 O(n²) 解析路径（未闭合 `<script>` 的 `.*?` 回溯、嵌套标签逐节点插入） | **单个请求就能把整个 API 冻住**：实测 480 KB 页面耗时 86.8s，期间进程内其它请求全部停摆；按二次增长外推到 5 MB 上限约 **2.5 小时** |
| **H1** | 投票去重按 `request.client.host` 算，而生产路径上这个值是 **Cloudflare 边缘 IP**，不是用户 IP | 同一浏览器在同一标签上**连投 3 次全部成功**；「同一 IP 同标签只能投一次」在真实入口上完全失效 |
| **H2** | 没有请求体上限，也没有分析并发上限 | 实测 30 MB POST 被完整收下（13.9s 后 422）；3 个并发分析 → 线程 3→12、RSS 104 MB→259 MB。t3.micro 只有 908 MB（其中 ~250 MB 是常驻），十来路并发就能打爆 |

同时也要说清楚：**开发者这轮补的 SSRF 防护是真的生效了**，不是纸糊的。DNS 重绑定、慢速滴流、chunked 陷阱、5 MB 上限、逐跳重定向校验、端口白名单、XFF 伪造，七项我都实测过，全部守住（证据见 §1、§2）。这次的窟窿不在网络层，而在**网络层之后**——拿到手的字节怎么解析、算出来的 IP 拿去当什么用。

## 严重

### S1 单请求 CPU 耗尽：`extract_text()` 的两条 O(n²) 路径把整个进程钉死

**问题.** 抓取只限制了「网络」成本（5 MB / 20s），没限制「解析」成本。`discover.extract_text()` 里有两处随输入平方增长的代码，输入完全由被抓取方控制：

1. `discover.py:221-222`：页面 > 400 000 字符时先做
   `re.sub(r"<script\b[^>]*>.*?</script>", "", html, flags=re.S|re.I)`
   `.*?` 带 DOTALL 且没有闭合标签时，每个 `<script` 起点都要把剩余全文扫一遍 → O(n²)。
2. `discover.py:235-238`：对每个 `_BLOCK` 元素做 `insert_before/insert_after`，嵌套越深越慢。

调用点：`pipeline.py:226`（首页没找到条款链接时）、`pipeline.py:299`（每份文档）、`discover.py:123`（补探的每条路径）。**这些判断都在 `looks_like_policy()` 之前**，也就是说页面像不像条款根本不影响它先把 CPU 烧掉。

**证据（本地跑的是线上同一份代码）.**
```
C:\...\backend> python t_dos.py
== A. 未闭合 <script> 触发的 re.sub 回溯 ==
  0.02 MB  <script>x2000    ->   0.094s
  0.06 MB  <script>x8000    ->   1.547s
  0.16 MB  <script>x20000   ->   9.711s
  0.40 MB  <script>x50000   ->  60.252s
== B. 嵌套 <div> -> extract_text ==
  0.05 MB  div x2000    ->   0.107s
  0.27 MB  div x10000   ->   1.926s
  0.54 MB  div x20000   ->   7.360s
  1.08 MB  div x40000   ->  28.948s
```
二次增长很明显：0.16→0.40 MB（2.5 倍）耗时涨 6.2 倍。按此外推，**5 MB 上限的页面约 2.5 小时**。

**这不是「慢一点」，是整站停摆。** `extract_text` 全程持 GIL（`re` 与 BeautifulSoup 都是纯 Python/C 且不释放），同进程的 asyncio 事件循环和其它请求线程全部排队：
```
C:\...\backend> python t_gil.py
payload size 480000
extract_text 耗时 86.8s
空闲 1s 心跳 98 次；运行期心跳 1 次（同长度空闲应约 8510 次）
```
心跳线程在 86.8 秒里只被调度到 **1 次**——uvicorn 是单进程，这等于整个服务对外失联 86.8 秒。

**影响面.** 无需任何凭据，一个请求即可：
```
GET /api/analyze?q=<攻击者自己的域名>
```
攻击者的站只要返回一份 `<script>` 重复 62 万次（约 5 MB）的 HTML 即可。10 次/分钟的限流在这里毫无意义——一次就够。`ANALYZE_BUDGET=65`（`pipeline.py:27`）也拦不住：它只在阶段之间检查，`extract_text()` 内部没有任何时间片。

**修法建议.**
- 解析前先截断：`html = html[:1_500_000]`（条款正文不需要 1.5 MB 以上）。
- 别用 DOTALL 正则剥 script：改用 `lxml.html` 的 `etree.HTMLParser(recover=True)` + `strip_elements(tree, "script", "style")`，或者 `html.parser` 一遍流式扫；一定要用正则就先 `html.count("<script")` 做硬上限。
- 去掉 `_BLOCK` 的逐节点 `insert_before/insert_after`，改用 `itertext()` + 块级标签换行的手写遍历。
- 兜底：把「分析」整体放进子进程（`multiprocessing`）跑，父进程 `join(timeout)`，超时直接 kill——线程杀不掉，进程可以。这一条同时能救 H2 的并发问题。

## 高

### H1 投票去重在真实入口上完全失效（Cloudflare 边缘 IP 冒充了用户 IP）

**问题.** `api.py:93` / `api.py:175` 用 `request.client.host` 作为身份；`api.py:183` 把它哈希成 `ip_hash` 参与去重（`api.py:186`）。但生产流量是 `浏览器 → lens.dohub.tech（CF Pages Function 代理）→ api.dohub.tech`，后端看到的对端是 **Cloudflare 边缘节点**，不是用户。

**证据 1：同一个客户端，三次请求，三个不同的「客户端 IP」.**
```
$ curl -s "https://lens.dohub.tech/api/analyze?q=zz"   ×3
$ sudo journalctl -u clauselens | grep 'analyze?q=zz'
INFO:     172.71.154.166:0 - "GET /api/analyze?q=zz HTTP/1.1" 200 OK
INFO:     104.22.17.72:0 - "GET /api/analyze?q=zz HTTP/1.1" 200 OK
INFO:     104.22.160.17:0 - "GET /api/analyze?q=zz HTTP/1.1" 200 OK
```

**证据 2：同一标签连投 3 次，全部成功.**
```
=== 3 votes via production path (lens -> CF -> api) ===
  #1 {"ok":true,"summary":{"collects-sensitive":{"agree":1,"disagree":0}}}
  #2 {"ok":true,"summary":{"collects-sensitive":{"agree":2,"disagree":0}}}
  #3 {"ok":true,"summary":{"collects-sensitive":{"agree":3,"disagree":0}}}
=== 2 votes direct to api.dohub.tech (same real IP) ===
  #1 {"ok":true,"summary":{"collects-sensitive":{"agree":4,"disagree":0}}}
  #2 {"detail":"这个标签你已经投过了"}
```
绕开前端直连 API 时去重是对的（第二次 409），**走产品自己的入口时就是提款机**。

**影响面.** 反馈数据是这条产品线的核心产出（AGENTS §5 的评测与标注都指望它）。现在任何人写十行脚本就能把任意域名、任意标签刷到任意比例；`/api/feedback/summary` 还是公开读的，刷完立刻能看到效果。数据一旦被污染无法回溯（没有去重键、没有来源可信度）。

**修法建议.** 二选一或并用：
1. 只信 `CF-Connecting-IP`，且仅在「对端 IP ∈ Cloudflare 官方段」时才信；Caddy 侧用 `trusted_proxies` + `{client_ip}` 落到 `X-Real-IP`，应用只读这个值。
2. 投票绑定服务端签发的匿名 cookie（HMAC，密钥在环境变量里），IP 只作为辅助维度。
另外把 `api.py:137` 的硬编码盐换掉（见 M3）。

### H2 没有请求体上限、没有分析并发上限

**问题 1：请求体不限.** `api.py:173` 的 `/api/feedback` 直接把 body 交给 pydantic；Caddy 侧 `api.dohub.tech` 块只有 `encode gzip` + `reverse_proxy`，没有 `request_body { max_size … }`；uvicorn 默认也不限。实测：
```
$ curl -X POST --data-binary @big.json  https://api.dohub.tech/api/feedback
code=422 time=13.90s up=30000090      # 30 MB 被完整收下并解析后才拒绝
```
一个字段 `comment` 限 200 字，但 body 本身可以 1 GB。并发几十个就能把 908 MB 的机器顶穿。

**问题 2：并发分析不限.** `api.py:112` 每个请求起一个线程，`pipeline.py:191` 每次再起一个 `ThreadPoolExecutor(1)`，`discover.probe_paths` 再来 6 个（`discover.py:101`），全都没有信号量。实测 3 路并发：
```
=== during ===
threads=12
VmRSS:   99676 kB
=== after ===
threads=3
VmRSS:  259484 kB        # 3 路把常驻从 ~104 MB 拉到 ~259 MB
```
systemd 记的另一组数更直观：该进程在一个 9.5 分钟的窗口里 **内存峰值 624.9 MB、swap 峰值 645 MB**（同期只有 10 次 analyze + 1 次 30 MB POST）。这台机器总共 908 MB，上面还跑着 wb2api 的容器。按线性外推，10–12 路并发就到红线；而「10 次/分钟」是**每 IP** 的，攻击者换 IP 即可；何况 S1 已经证明根本不需要并发。

**修法建议.** Caddy 加 `request_body { max_size 256KB }` 给 `/api/feedback`（或全局 + 对 analyze 例外）；应用侧加一个 `BoundedSemaphore(2~3)` 限制同时分析数，排队超过 N 个直接返回 429；`/api/analyze` 用子进程 + 硬超时（同 S1 的兜底）。

## 中

### M1 限流键在生产路径上是 Cloudflare 边缘 IP：共享桶、互相误伤，且源站 IP 公开可直连

同 H1 的根因，但影响不同：`api.py:70-83` 的 `_hits` 按「对端 IP」计数。走 `lens.dohub.tech` 的用户，被随机分配到 CF 的若干边缘 IP 上，**同一出口 IP 后面的所有用户共享 10 次/分钟**——高峰期会互相把对方限掉，而错误提示是「查得太快啦」，用户完全无法理解。

同时 `api.dohub.tech` 是**灰云（DNS-only）**，A 记录直指源站 IP（此处已隐去），响应头里没有 `cf-ray`、只有 `Server: uvicorn` / `Via: 1.1 Caddy`。也就是说：Cloudflare 的 WAF / DDoS 防护对 API **完全不生效**，攻击者绕过前端直打源站，唯一的防线就是应用内那 10 次/分钟。

```
$ curl -D - https://api.dohub.tech/api/taxonomy
HTTP/1.1 200 OK
Server: uvicorn
Via: 1.1 Caddy
（无 cf-ray / cf-cache-status）
```

**修法建议.** 要么把 API 也挂到 Cloudflare（橙云 + Authenticated Origin Pulls），要么在 Caddy 前面加一层真正的限流（caddy-ratelimit 或 nginx `limit_req`）；应用内限流继续保留作为第二道。

### M2 安全响应头基本没有；前端可被点击劫持

**API（api.dohub.tech）**实测只有 `Server: uvicorn`——没有 HSTS、没有 CSP、没有 `X-Content-Type-Options`、没有 `X-Frame-Options`、没有 `Referrer-Policy`：
```
$ curl -D - -o /dev/null https://api.dohub.tech/api/taxonomy
HTTP/1.1 200 OK
Server: uvicorn
Vary: Origin
Via: 1.1 Caddy
```
- 缺 HSTS：`http://` 目前是 308 跳转（实测），但首跳仍可被降级劫持。
- `Server: uvicorn` 直接告诉扫描器「后端是 Python/uvicorn」，配合 M5 的 `/docs` 更好打。

**前端（lens.dohub.tech）**有 `Strict-Transport-Security: max-age=15552000`、`x-content-type-options: nosniff`、`referrer-policy: strict-origin-when-cross-origin`，但**没有 CSP、没有 X-Frame-Options**，并且 `Access-Control-Allow-Origin: *`。
```
$ curl -D - -o /dev/null https://lens.dohub.tech/
Access-Control-Allow-Origin: *
Strict-Transport-Security: max-age=15552000
x-content-type-options: nosniff
referrer-policy: strict-origin-when-cross-origin
Server: cloudflare
（无 content-security-policy / x-frame-options）
```
站点里有投票按钮，`X-Frame-Options` 缺失意味着可以被嵌进 iframe 做**点击劫持投票**（与 H1 叠加，刷票连脚本都不用写）。`dist/index.html` 里也没有 `<meta http-equiv="Content-Security-Policy">`。

**修法建议.** Caddy 给 `api.dohub.tech` 加：
```
header {
  Strict-Transport-Security "max-age=31536000; includeSubDomains"
  X-Content-Type-Options "nosniff"
  Referrer-Policy "no-referrer"
  -Server
}
```
前端在 Pages 根目录加 `_headers`：`X-Frame-Options: DENY` + `Content-Security-Policy: frame-ancestors 'none'; default-src 'self'; connect-src 'self'`（注意 `connect-src` 要放行 `/api`）。

### M3 `ip_hash` 的盐是硬编码常量，IP 可被反推

`api.py:137`：`FB_IP_SALT = "clauselens-vote"`，注释还写着「不是安全哈希」。但 IPv4 只有 2³² 个值，已知盐 + 12 位十六进制 → 秒级穷举。我直接验证了：

```
$ grep audit-probe data/feedback.jsonl | head -1
{"domain":"audit-probe.example", ..., "ip_hash":"8a389fe2ad81", "at":"..."}

$ python3 -c 'import hashlib;print(hashlib.sha1(b"clauselens-vote|104.22.20.8").hexdigest()[:12])'
8a389fe2ad81
```
`1ac3c7cce3da` 也对上了我自己的出口 IP `（本机出口 IP，已隐去）`。所以 `data/feedback.jsonl` 里的「匿名」IP 哈希可以还原成真实 IP；再叠加 `domain` + `tag_id` + `vote` + 秒级时间戳，等于一份可去匿名化的用户行为日志。如果这条产品线要对外/出海，这是 GDPR/《个人信息保护法》意义上的个人信息。

**修法建议.** 盐改成环境变量里的随机值；或者干脆不存 IP 哈希，改存服务端会话 ID（同样只用于去重，且随会话过期）。

### M4 uvicorn 以 `--forwarded-allow-ips=*` 运行

`/etc/systemd/system/clauselens.service`：
```
ExecStart=... uvicorn clauselens.api:app --app-dir backend --host 127.0.0.1 --port 8787 \
          --proxy-headers --forwarded-allow-ips=*
```
「信任任何来源的 `X-Forwarded-For`」。目前 8787 只监听 `127.0.0.1`（`ss -lntp` 实测），外面进不来，所以**现在不构成漏洞**；但它把「限流/去重的身份」完全交给了「谁能碰到这个 socket」。一旦哪天为了排障改成 `--host 0.0.0.0`、或者加一层不覆写 XFF 的代理，H1 就会从「CF 边缘 IP」退化成「攻击者随便写」。

**证据：XFF 伪造在当前链路下不成立**（这条是好消息，见 §2）：
```
$ curl -H "X-Forwarded-For: 203.0.113.77" "https://api.dohub.tech/api/analyze?q=zz"
$ sudo journalctl -u clauselens | grep 'analyze?q=zz' | tail -1
INFO:     （本机出口 IP，已隐去）:0 - "GET /api/analyze?q=zz HTTP/1.1" 200 OK   # 我自己的真实 IP
```
**修法建议.** `--forwarded-allow-ips=127.0.0.1` 即可。

## 清单逐条结论

### 1. 抓取面（SSRF）—— **网络层通过，解析层失守**

| 检查项 | 结论 | 证据 |
|---|---|---|
| 内网地址（字面量） | 拦住 | `127.0.0.1` / `169.254.169.254` / `[::1]` / `2130706433` / `0x7f000001` → `bad_input` |
| 内网地址（DNS 指向内网） | 拦住 | `127.0.0.1.nip.io` / `localtest.me` / `169.254.169.254.nip.io` → 解析层拒绝；服务器 tcpdump `lo` 上 `:8080` **零包** |
| DNS 重绑定 | 拦住 | 0.02s `blocked`，见上表 |
| 重定向链（内网 / file / gopher / ftp / 相对） | 拦住 | 见上表 |
| 端口探测 `:22 :6379 :9200` | 拦住 | 0.01s 拒绝 |
| 超大响应 | 拦住 | 5 MB 截断 |
| 慢速滴流 | 拦住 | 6.00s |
| chunked 陷阱 | 拦住 | 7.00s |
| `load_snapshot()` 穿越 | 拦住 | 6 种写法全 None |
| **抓回来的 HTML 的解析成本** | **❌ 没有上限** | **S1** |
| IPv6 边角（`::ffff:0:127.0.0.1`） | 理论可过，实际连不通 | L9 |

### 2. 认证与滥用 —— **不合格**

- **需要认证的接口**：一个都没有。`/openapi.json` 里只有 4 个路由，全部匿名（这本身符合产品定位：公开查询工具）。
- **`/api/feedback` 刷票**：✅ 可刷（H1 实测 3/3）。
- **限流被 XFF 伪造绕过**：❌ 不成立——Caddy 覆盖了客户端自带的 XFF，实测伪造无效。**但**限流的键在生产路径上是 CF 边缘 IP（M1）。
- **`nocache=1` 公开滥用**：确认公开且无任何限制（`api.py:92`）。任何人 `?nocache=1` 都强制真实抓取，配合 S1 就是「一键打瘫」的开关。
- **单 IP 耗尽资源**：确认。3 路并发 → 12 线程 / +155 MB（H2）；而 S1 连并发都不需要。

### 3. 信息泄露 —— **基本通过**

- 错误信息：全是中文人话，`internal` 分支（`api.py:108-109`）吞掉异常细节，未见栈/路径/内网 IP。422 只回 pydantic 的字段级信息。
- `/api/taxonomy`：公开且只有标签定义（13 KB），无敏感内容。
- 响应头：见 M2（缺 HSTS/CSP/XFO/nosniff，`Server: uvicorn`）。
- 前端产物：抓了线上 `index-CFzdToGQ.js`（418 639 B）全量扫 `AKIA/sk-/api_key/secret/token/password/内网段/api.dohub.tech`，**只命中 React 内部的 `password` input 类型**，无硬编码密钥、无内网地址。
- `data/feedback.jsonl` / `data/cache/` 经 HTTP 不可达：服务器上根本没有 `frontend/dist`，SPA 路由未注册（`api.py:211`），`/../data/feedback.jsonl`、`/..%2f..%2f…`、`/%2e%2e/…`、`/assets/..%2f…` 全部 **404**；前端侧 CF 直接 **400**。
- 附带的隐私问题：`ip_hash` 可反推真实 IP（M3）。

### 4. 传输与配置 —— **传输合格，配置偏松**

| 项 | 结论 | 证据 |
|---|---|---|
| TLS 1.0 / 1.1 | 拒绝 | `TLSV1_ALERT_PROTOCOL_VERSION` |
| TLS 1.2 / 1.3 | 可用 | `ECDHE-ECDSA-AES128-GCM-SHA256` / `TLS_AES_128_GCM_SHA256` |
| 弱套件（CBC/3DES/RC4） | 全部拒绝 | `AES128-SHA` / `DES-CBC3-SHA` / `RC4-SHA` 均 rejected |
| 证书链 | 有效 | Let's Encrypt YE2，SAN=`api.dohub.tech`，2026-11-11 → 2027-02-09，`Verify return code: 0 (ok)`，链到 ISRG Root X2 |
| HTTP → HTTPS | 308 | `Location: https://api.dohub.tech/...` |
| Caddy 暴露面 | 只有 2 个站 | 另一面板站（与本项目无关，细节已隐去）+ `api.dohub.tech`；后者只有 `encode gzip` + `reverse_proxy`（M2 缺头、H2 缺 body 限制） |
| 外部端口 | 22 / 80 / 443 | 14 个端口逐个 TCP 连接：只有这 3 个 OPEN，7863/7864/8443/8787/18080/6379/9200 等全 closed |
| ufw | active | default deny incoming；只放 22/80/443（v4+v6） |
| AWS 安全组 | 与 ufw 一致 | 外部实测只有 3 个端口通 |
| PSI | 无压力 | `some avg10=0.00`；内存 908 MB / swap 4 GB（审计开始时 swap 用了 201 MB，并发测试后 swap 峰值一度到 645 MB） |

### 5. 依赖与代码 —— **无 RCE，ReDoS 在自家代码里**

- `eval` / `exec` / `pickle.loads` 用户可控输入：**没有**。全仓 grep 只有 `detect.py:102` 的 `pickle.load(f)`，读的是 `data/models/*.pkl`（内置可信文件），符合任务说明里的豁免。
- 正则回溯：**有，而且是致命的**——不在 taxonomy，在 `discover.py:221-222`（S1）。taxonomy 的 36 个标签 × 6 条恶意句跑完只要 **0.009s**；`_DOMAIN_RE` 100 次 0.000s；`_meta_site_name` 对 200 KB 畸形 meta 0.002s。**唯一的问题点是 `extract_text`。**
- 依赖 CVE：soupsieve 2.8 五条（M6），其余干净。

### 6. 业务逻辑 —— **通过**

- `target="_blank"` 两处（`Reader.jsx:277`、`Result.jsx:133`）**都带了 `rel="noreferrer noopener"`**。
- `dangerouslySetInnerHTML` / `innerHTML`：**零命中**；所有抓回来的原文、`quote`、站点名都走 React 文本节点转义。
- 阅读器渲染：`Reader.jsx:47-93` 是把 `text` 按 `spans` 切片成 `<mark>` + 文本节点，没有 HTML 注入面；`doc.url` 只会是 http/https（服务端只抓这两种，且逐跳校验）。
- 结论：**没有 XSS 面**。真正的问题不在这，在投票数据完整性（H1）和可用性（S1/H2）。
