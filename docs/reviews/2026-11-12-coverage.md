# 站点覆盖测试报告 · 2026-11-12

> 对象：线上条款分析服务 `https://lens.dohub.tech`（`GET /api/analyze?q=`，SSE）
> 角色：只读覆盖测试。**没有改动 `backend/` 下任何代码**、没有重启服务、没有改配置。写入物只有本报告、`scripts/bench/coverage.py`、`scripts/bench/coverage_sites.json`，以及 `out/` 下的原始结果。
> 方法：40 个真实站点 × 两种输入（模糊 `q=<域名>` / 精确 `q=<条款页 URL>`），串行打线上接口，逐个记录失败码 + **SSE 阶段轨迹**；失败站再用 `curl` 与后端同一套 `extract_text()` / `looks_like_policy()` 复判，判断卡在哪一步。
> 代码基线：本地工作副本；`backend/clauselens/` 下 `pipeline.py`、`discover.py`、`net.py`、`api.py`、`render.py` 的行号引用均针对这份文件。
> 数据：`out/coverage.jsonl`（77 条原始记录）、`out/diag.json`（14 条失败诊断）、`out/run.log`（逐条过程日志）。

## 总评

覆盖率的表面数字是**模糊 80.0% / 精确 83.8%**，但这个数字**严重高估**了真实能力：

| 口径 | 模糊 | 精确 | 说明 |
|---|---|---|---|
| 表面成功率 | **32/40 = 80.0%** | **31/37 = 83.8%** | 只要回了 `result` 就算成功 |
| 扣除「靠缓存/registry 快照」 | 17/40 = **42.5%** | 21/37 = **56.8%** | 这 15 + 10 条**根本没实时抓到**，是靠预先存好的正文 |
| 再扣除「内容判错」 | 17/40 = **42.5%** | 19/37 = **51.4%** | s09 精确模式命中的是淘宝**错误页**，s36 精确模式命中的是支付宝**首页 185 字** |

也就是说：**一个我们没预存过的站，模糊模式有四成多概率查不到。** 预存快照撑起了近一半的"成功"。

最该先修的两件事，都不是"对方不让抓"，而是**我们自己的发现与渲染**：

1. **裸域失败就放弃** —— s07 `cosmoplat-aiot.com` 裸域证书校验失败，但 `www.cosmoplat-aiot.com/policy-agreement/1.html` 是**静态 13144 字**的隐私政策，一个字都不用渲染。我们却直接判 `not_found`。
2. **渲染兜底有效率只有 43%** —— 14 次走渲染，8 次拿到正文，其中 2 次拿到的是错误页/首页；真正有效的只有 6 次。

另外发现三类"假成功"（§6）：**错误页被当隐私政策**、**首页 185 字被判成条款**、**WAF 拦截页把 Cloudflare 自己的隐私政策算成了对方站点的条款**（还被缓存 24 小时）。

> ⚠️ 一条口径提醒：测试窗口内仓库有并行改动，渲染器在 04:00 被换成 Lightpanda（在我测试结束之后）。**§4 / §5 里与渲染相关的结论只代表 03:23–03:56 那版线上服务**，详见附录 C。

## 一、测试方法

**站点来源**：全部经 anysearch 检索或本仓库既有实测记录确认存在，`scripts/bench/coverage_sites.json` 里每个站都写了 `provenance` 字段。类别配比按要求：国内中小厂 8、国内大厂 5、国外中小 SaaS 8、国外大厂 5、典型 SPA 6、电商金融 4、论坛社区 4。

**条款路径怎么定的**：先 `curl` 首页，按 `<a>` 的 href 与锚文本打分取最像条款的链接；首页没有链接才探 8–16 条常见路径，并用 `looks_like_policy()` 复判。3 个站确认无公开条款页（s01 `tool.lu`、s03 `appinn.net`、s04 `luolei.org`），精确模式跳过，共 **77 次调用**。

**关于限流的一条更正**：任务说明里是"并发上限 3、间隔 ≥1 秒"，实测**还有一道每 IP 10 次/60 秒的滑动窗口**（`backend/clauselens/api.py:94`，`limit=10, window=60`），超了回 `code: rate_limited`「查得太快啦，歇一分钟再来」。第一轮按 1.5 s 间隔跑，第 8 个站就开始连续吃 `rate_limited`。最终脚本内置同节奏的滑动窗口（留 1 次余量，实际 9 次/窗口），77 次调用期间只漏进 3 次，均按 62 s 重试恢复。**这个限制没有写进任何文档**，做压测或前端自动重试时很容易踩。

**约束遵守**：单站最多 2 次调用（模糊 + 精确），未超 3 次；全程串行；`busy` 与 `rate_limited` 分别等 15 s / 62 s 重试；读超时 200 s。

## 三、成功率

```
模糊模式    32/40 = 80.0%   其中实时抓取 17、缓存/快照 15（占成功的 47%）
精确模式    31/37 = 83.8%   其中实时抓取 21、缓存/快照 10（占成功的 32%）
合计        63/77 = 81.8%
```

**按真实抓取能力算**（扣除未实时抓取的 25 条）：

```
模糊 17/40 = 42.5%      精确 21/37 = 56.8%
再扣 2 条内容误判 →     精确 19/37 = 51.4%
```

分类型看，短板非常集中：

| 类型 | 模糊 | 精确 | 备注 |
|---|---|---|---|
| 国内中小厂/工具站 | **2/7 = 29%** | 3/5 = 60% | 最差的一类，且两条"成功"还是缓存 |
| 国内大厂 | **5/5**（4 条靠缓存） | 3/5 = 60% | 三条失败全是 JS 渲染页 |
| 国外中小 SaaS | 8/8 | 7/8 | 最好的一类 |
| 国外大厂 | 4/5 | 4/5 | 唯一失败是 Notion 挂死 |
| 典型 SPA | 5/6 | 6/6 | 6 条靠缓存 |
| 电商/金融 | 4/4 | 2/4 | PayPal 403、支付宝拿到首页 |
| 论坛/社区 | 3/4 | 3/4 | Lobsters 正文 125 字 |

结论很清楚：**domestic 中小站 + 中文 JS 渲染页**是两块洼地；国外中小 SaaS 反而覆盖得不错（服务能走境外出口，且这些站大多是静态/Next.js SSR，条款页直链清晰）。

## 四、「浏览器能打开，我们却查不到」

这是最该修的一类。判定标准：**该页面在真实浏览器里能正常显示条款正文**，而我们返回了错误。逐条给了卡点证据。

| 站点 | 我们返回 | 浏览器侧证据 | 卡在哪一步 | 根因 |
|---|---|---|---|---|
| **s07 cosmoplat-aiot.com** | 模糊 `not_found` | `/policy-agreement/1.html` **静态 13144 字**，`curl` 直接可取，无需 JS | 首页就没打开：`{"stage":"discover","message":"首页打不开（打不开这个网站），试试常见路径"}`，随后 `found: 0` | **裸域 TLS 失败未回退 www** + **兜底路径表没有中文站的 `/policy-agreement/`** |
| **s11 bilibili.com** | 精确 `not_found` | 外部抓取确认标题「哔哩哔哩隐私政策」，正文完整 | `fetch` → `render`（`"「/blackboard/privacy-pc.html」正文要跑脚本才有，正在用浏览器渲染"`）→ 渲染后正文仍为空 | **渲染器没拿到这份 SPA 条款页的正文** |
| **s02 xiezuocat.com** | 模糊 + 精确都 `not_found` | `/privacy` 浏览器可见条款 | 模糊：`"已渲染首页（1178 字）"` 但**渲染后的首页里找不到任何条款链接**；精确：`fetch` → `render` 后正文仍 149 字空壳 | **前端路由站的条款既不在首页链接里、也不在 `/privacy` 的静态/首屏 HTML 里** |
| **s23 notion.so** | 模糊 `client_error`(138 s) / 精确 `no_result`(128 s) | 浏览器可正常打开 | 精确模式走到 `fetch` → `render` 后**再无任何事件**；`www.notion.com/privacy` 对任何非 JS 客户端返回 **401** | **渲染卡死 + SSE 无终结事件**（详见 §5.4） |
| s35 paypal.com | 精确 `blocked_by_site 403` | 浏览器可开 | `fetch` 403 → `render` 兜底仍 403 | **Cloudflare 对无头浏览器同样拦截**（换浏览器 UA 仍 403） |
| s05 ezg.com | 精确 `blocked_by_site 403` | 浏览器（带 JS/cookie）可开 | `fetch` 403 → `render` 仍 403 | 同上，Cloudflare 托管挑战 |

**必须区分清楚**：s07 / s11 / s02 / s23 是**我们自己的问题**（页面内容本来就能拿到，或我们承诺了渲染兜底却没用）；s05 / s35 是**对方主动拦截**，属于对抗成本问题。

**不是缺陷的两条**（判 `not_found` 正确，列出来避免误修）：

- **s01 tool.lu**：`/privacy`、`/terms`、`/about` 全部 404（同一份 226 字节 404 页），首页也没有任何条款链接 —— 该站**确实没有公开条款页**。
- **s04 luolei.org**：个人博客，无条款页。

**s39 lobste.rs 属于判据边界**：`/privacy` 是真的隐私政策页，但正文只有 125 字（"This is the Internet, you have no privacy."）。`looks_like_policy()` 要求 ≥150 字（`backend/clauselens/discover.py:300`），所以判死。从"给用户看条款分析"的角度，这个结果**可以接受**，但它暴露了硬下界的脆弱性。

## 五、失败清单与根因分类

### 5.1 `not_found` × 8

| 站点 | 模式 | 复判证据 | 根因 |
|---|---|---|---|
| s01 tool.lu | 模糊 | 首页 200 / 2608 字，`home_link_n=0`；`/privacy` `/terms` `/about` 全 404 | **站点无条款页**（非缺陷） |
| s02 xiezuocat.com | 模糊 | 首页渲染后 1178 字，但 0 条条款链接 | **发现失效**：SPA 首页无静态/渲染后条款链接 |
| s02 xiezuocat.com | 精确 | `/privacy` = 8827 字节空壳，正文 149 字；渲染后仍空 | **渲染失效** |
| s04 luolei.org | 模糊 | 首页 200 / 655 字，0 条条款链接 | **站点无条款页**（个人博客，非缺陷） |
| s07 cosmoplat-aiot.com | 模糊 | 裸域 `SSLCertVerificationError`；www + `/policy-agreement/1.html` = 13144 字 | **裸域 TLS 未回退** + **路径表缺中文路径** |
| s11 bilibili.com | 精确 | 页面 2385 字节、`spa_shell=true`、正文 0 字；渲染后仍 0 | **渲染失效** |
| s39 lobste.rs | 模糊 | 首页 2460 字，0 条条款链接 | 条款页没从首页链出来（`/privacy` 存在） |
| s39 lobste.rs | 精确 | `/privacy` 200，正文 125 字 | **正文过短被判死**（阈值 150 字） |

> 注意 s39 模糊与精确是两种不同原因：模糊是**发现不到**（首页没链），精确是**认不出**（太短）。`looks_like_policy` 与发现是两道独立的坎。

### 5.2 `unreachable` × 2

| 站点 | 复判证据 | 根因 |
|---|---|---|
| s03 appinn.net | 裸域 **DNS 解析失败**（NameResolutionError）；`www.appinn.net` 返回 **200**，正文 3604 字 | **裸域无记录，www 正常** —— 用户输 `appinn.net`，浏览器多数情况下会补 www 打开，我们不会 |
| s31 doulor.cn | 裸域 `ConnectTimeout`；`cloud.doulor.cn/privacy` 有 1271 字快照 | **裸域不可达，子域/`cloud.` 正常** |

两条都不是"站点挂了"，而是**输入归一化缺失**：拿到域名后一律拼 `https://<域名>/`（`backend/clauselens/pipeline.py:221`），失败就判 `unreachable`，**从不尝试 `www.`**。

> 口径说明：`unreachable` 只代表"**从服务端**连不上"。我这台测试机在国内网络，对境外站（notion / spotify / discord / twitch / doulor）本地大量连接被重置，与服务侧结论并不一致 —— 服务侧对这些站的实时抓取多数是成功的（s24/s25/s26 均实时或缓存成功）。因此本报告**没有**用本地连通性去推翻服务侧的 `unreachable` 判定，只对 s03/s31 做了"另一条路径能通"的正面证据。

### 5.3 `blocked_by_site` × 2

| 站点 | 状态码 | UA 对比 | 判断 |
|---|---|---|---|
| s05 ezg.com（精确） | 403 | 换真实 Chrome UA 仍 **403**，页面标题 `Attention Required! \| Cloudflare` | Cloudflare 托管挑战。服务已按 `pipeline.py:288` 用渲染兜底，仍 403 → **无头浏览器指纹没过 CF** |
| s35 paypal.com（精确） | 403 | 换 UA 仍 **403**，页面 43 字 | 同上。paypal 对 `legalhub/privacy-full` 严格拦脚本 |

两条都是**真实的"对方拒绝"**，`blocked_by_site` 判定准确，用户看到的提示也基本准确。可改进的是提示文案：现在说"可以换一个能打开的镜像站点"，但用户在自己浏览器里明明能打开，真正可行的动作是**把整条 URL 粘进来让我们渲染**（对 s05 无效，对 s35 也无效）——提示给了错误的方向。

### 5.4 `client_error` / `no_result` × 2：s23 Notion（最严重的健壮性缺陷）

- 模糊：`client_error: ChunkedEncodingError: Response ended prematurely`，**138.2 s**
- 精确：`no_result`（既无 `result` 也无 `error` 事件），**127.9 s**，阶段停在 `resolve > discover > fetch > render`

诊断：`https://www.notion.com/privacy` 对浏览器 UA 返回 **401**（22980 字节、34 个 `<script>`、正文 88 字）。服务按 `pipeline.py:288` 走渲染兜底，然后**就没有然后了**——流被掐断，前端只能一直转圈。

两个独立问题叠在一起：

1. **渲染超预算**：`ANALYZE_BUDGET = 65 s`（`pipeline.py:27`），实际跑了 128–138 s，预算没兜住。
2. **SSE 没有终结事件**：`api.py:139` 的异常兜底会推 `{"code":"internal"}`，但这条路径没走到；前端拿到的是一个"安静死掉"的流。这是用户视角最糟的失败形态——比报错还糟，因为它没有终点。

## 六、顺带发现的三个「假成功」

覆盖率不只被"漏判"高估，也被"误判"高估。这三条都返回了 `result` + 等级，但内容不是该站的条款：

| 站点 | 我们返回 | 实际是什么 | 证据 |
|---|---|---|---|
| **s05 ezg.com**（模糊） | ✅ 1 篇 / 17282 字，等级 C | **Cloudflare 自己的隐私政策** `https://www.cloudflare.com/zh-cn/privacypolicy/` | 结果来自 24 h 缓存（`{"cached": true}`）；该站被 CF 拦成 403，拦截页里的 CF 政策链接被当成对方条款；`discover.py:175,184` 对跨域链接只扣 3 分、不否决 |
| **s09 taobao.com**（精确） | ✅ 1 篇 / **976 字**，等级 C | 淘宝**错误页** `https://error.taobao.com/tbpc/error.html?from=...privacy_policy.php` | 条款页 302 到 error 页，`looks_like_policy()` 放行了 976 字错误页 |
| **s36 alipay.com**（精确） | ✅ 1 篇 / **185 字**，等级 C | 支付宝**首页** `https://www.alipay.com/`，type=other | 渲染后拿到 185 字首页文案，过了 150 字下界 + 关键词密度（`discover.py:306`） |

这直接违背了 `AGENTS.md` §5 的"宁可未发现也不乱贴负面标签"：给 Cloudflare 的政策打出"允许把信息分享给广告商"的结论，挂在 `ezg.com` 名下，用户点开证据看到的却是 cloudflare.com 的原文 —— 这会直接摧毁可信度。而且错误结果被缓存 24 h（`pipeline.py:23,178`）。

同类但程度轻的三条（列出来供定阈值参考）：s10 京东模糊模式混入了 508 字的**商品营销页**（`global.jd.com/user-agreement`）；s29 Supabase 模糊模式混入 421 字的 **Legal Hub 目录页**；s35 PayPal 模糊模式拿到的是 525 字的**隐私设置面板**（`myaccount/privacy/privacyhub`），不是完整声明。

## 七、改进建议（按可修复性排序）

排序依据：**改动量 × 能救回的站点数 × 风险**。

### 1. 裸域失败自动回退 `www.`（最容易，立竿见影）

- **改哪**：`backend/clauselens/pipeline.py:221` 首页抓取包一层 —— `https://<域名>/` 失败（`unreachable` / `timeout` / `SSLCertVerificationError`）后改试 `https://www.<域名>/`；`net.fetch()` 内部对证书校验失败也走同一回退。
- **救回**：s07（13144 字静态条款页）、s03（www 200）、s31（`cloud.` 子域）。
- **代价**：一次额外请求，只在失败时发生；对已成功的站零影响。
- **衡量口径**：`unreachable` 占比应从 2/40 降到 ≈0。

### 2. 补中文站常见条款路径，并把探测预算从 14 条放开

- **改哪**：`backend/clauselens/discover.py:20` 的 `COMMON_PATHS` 现 38 条，**一条中文语义路径都没有**（全是 `/privacy`、`/legal/*`）。补：`/policy-agreement/`、`/policy-agreement/N.html`、`/agreement`、`/protocol`、`/protocols/`、`/about/policy`、`/statement`、`/privacy-policy-cn`。
- **更要紧的一处**：`backend/clauselens/pipeline.py:249` 是 `limit=24 if not home_cands else 14` —— **首页只要发现了一两条候选，探测预算就砍到 14 条**，正好把新补的中文路径挤在门外。建议改成"按已发现的类型缺口排序后在完整表里取前 N"，而不是按表头顺序取。
- **救回**：s07（`/policy-agreement/1.html`），并显著提升国内中小站那一类（当前模糊 2/7）。
- **代价**：补探并发已受限（`probe_paths` 内部有 deadline），加路径不必然加时延；建议按 `doc_type` 补齐优先于按顺序。

### 3. 渲染兜底：失败要能识别，别只试一次

- **现状实测**：14 次走渲染，8 次拿到正文，其中 s09/s36 拿到的是错误页和首页 → **真正有效 6 次，有效率 43%**；3 次 `not_found`（s02 精确、s11 精确、s39 精确）都是"渲染了但正文仍 <150 字"。
- **改哪**：`backend/clauselens/render.py:23` 当前 `RENDER_TIMEOUT_MS=25000`，`networkidle` 只给 1/3 预算（`render.py:189`）。对 Vue/React 路由页建议：① 正文仍为空时等待 `networkidle` 满额 + 滚动一次再取；② SPA 直接读 `__NEXT_DATA__` / `window.__INITIAL_STATE__` / `<script type="application/json">` 里的正文，往往比等 DOM 更可靠；③ 记录"渲染成功但正文为空"，让上层能区分"渲染器没跑"和"跑了没内容"。
- **救回**：s02、s11；间接改善 s23。
- **代价**：中等，涉及渲染器行为；建议加开关，先在灰度里对比有效率。

### 4. SSE 必须有终结事件（体验硬伤，改动小）

- **改哪**：`backend/clauselens/api.py:139` 的兜底没覆盖到"生成器卡住/连接被掐"这条路径。建议：给整个生成器套**硬超时 watch（`ANALYZE_BUDGET` 到点强制 yield `error: timeout`）**，并在 `StreamingResponse` 上确保任何退出路径都推一条终结事件。
- **为什么优先**：用户视角这是最糟的失败形态。128 s 转圈然后静默断开，比"3 秒告诉我不行"差得多。同时 `pipeline.py:27` 的 65 s 预算在 s23 上没有生效，值得单独查。
- **衡量口径**：`no_result` / `client_error` 应为 0。

### 5. 收紧判据，别再让错误页和首页冒充条款（可信度）

- **改哪**：`backend/clauselens/discover.py:292-307`。
  - 加**否决项**：最终 URL 或标题命中 `error`、`404`、`not-found`、`expired` 直接拒；URL 路径为空（就是首页）且字数 <400 直接拒。
  - 短页（150–600 字）现在只要求密度 `hits >= 4 and hits*150 >= len`（`discover.py:306`），185 字的支付宝首页就是这么过的。建议短页再加一条"必须命中 ≥2 个**法律主体类**关键词"（我们/本公司/个人信息处理者/适用法律/privacy policy/controller）。
- **救回**：s09 精确、s36 精确两条假成功。
- **代价**：小，纯判据。

### 6. 跨域归因：被 WAF 拦时不要相信对方的政策链接

- **改哪**：`backend/clauselens/discover.py:175,184` 对跨域链接只 `s -= 3`，不否决。建议：**当目标站本次抓取拿到 4xx/5xx 时，跨域候选一律否决**；即使正常，跨域命中也要在结果里标注"法域/集团站点"，避免把 cloudflare.com 的政策挂到 ezg.com 名下。
- **同时**：`pipeline.py:23` 的 24 h 缓存会把错误结论固化一整天，建议对"文档全部跨域"或"正文 <400 字"的结果**不入缓存**。

### 7. 战略层：别让快照掩盖真实覆盖率

模糊 15/32、精确 10/31 的成功来自 registry/缓存。这不是坏事（它对用户更快更稳），但它**掩盖了抓取能力的真实水位**（42.5% / 51.4%）。建议在 `scripts/bench/` 里把本脚本固化成回归项，跑的时候用**全新域名**（清缓存 + 不给快照），否则覆盖率指标会一直虚高。另外 3 条假成功说明"成功"的定义要看内容对不对，不能只看 `result` 有没有回来。

## 八、脚本用法

脚本在 `scripts/bench/coverage.py`，站点表在 `scripts/bench/coverage_sites.json`（换一份即换测试集）。

```bash
# 1) 探测条款路径：补全站点表里的 policy_url（只读目标站，不打我们的接口）
python scripts/bench/coverage.py probe --sites scripts/bench/coverage_sites.json

# 2) 跑覆盖矩阵（串行 + 限流内建，默认 9 次/60s；busy 等 15s，rate_limited 等 62s 重试）
python scripts/bench/coverage.py run --out out/coverage.jsonl --interval 1.0 --rate-limit 10

#    只跑某几个站 / 断点续跑 / 先跑 5 次试水
python scripts/bench/coverage.py run --only s02,s07,s11 --out out/coverage.jsonl
python scripts/bench/coverage.py run --resume --out out/coverage.jsonl
python scripts/bench/coverage.py run --max-calls 5 --out out/coverage.jsonl

# 3) 失败根因诊断（用服务同款 extract_text / looks_like_policy 复判）
python scripts/bench/coverage.py diagnose --results out/coverage.jsonl --out out/diag.json
python scripts/bench/coverage.py diagnose --results out/coverage.jsonl --only-codes not_found

# 4) 生成 markdown 总表
python scripts/bench/coverage.py report --results out/coverage.jsonl
```

几条实现上的注意：

- **节流是脚本内建的**，不是靠 `sleep`。`Pacer` 维护滑动窗口，按服务那道 10 次/60 秒的闸门排队（留 1 次余量），`--interval` 只管最小间隔。
- **判据与服务对齐**：脚本能 import `backend/clauselens/` 时，直接复用 `discover.extract_text()`、`discover.looks_like_policy()`、`net.decode_body()`（开跑第一行会打印 `判据=backend.discover+net.decode_body`）。import 不到就退化成内置正则版，并在输出里标注 —— 这样本地复判的结论和服务线上行为可比。
- **`stages` 字段是排障主力**：每条记录都存了 SSE 的完整阶段轨迹。`not_found` 到底是"没发现"还是"发现了但渲染没拿到"，看它有没有 `fetch` / `render` 阶段就能分开（§5 全部结论都是这么得出的）。
- **结果性质要自己算**：`documents` 有没有 `snapshot_at`、`stages` 里有没有 `fetch` / `cached`，决定这条"成功"是不是真的抓到了。只看 `ok` 会把覆盖率读高 30–40 个百分点。
